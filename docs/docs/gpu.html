GPU scheduling

Exercise GPU-aware charts and Kubernetes scheduling contracts today, without pretending the Apple GPU is already available inside a node VM.

No hardware acceleration in mock mode --gpu-mock advertises a synthetic extended resource. It does not expose the Apple GPU, Metal, CUDA, or Vulkan acceleration.
kiac create cluster --name gpu-lab --workers 2 --gpu-mock

The flag works on both kubeadm and k3s. It is fully opt-in: clusters created without it have no device-plugin Pods and no additional startup or idle overhead.

What gets installed

PieceContract
Extended resourceOne synthetic kiac.dev/gpu on every current node
RuntimeClasskiac-gpu, passed through to the existing runc handler
Device pluginsquat/generic-device-plugin 0.2.0, pinned by multi-architecture digest, in kiac-gpu-system
Allocation markerThe harmless node device /dev/null, mounted into requesting Pods at /dev/kiac-mock-gpu
Node labelsgpu.present=true, product=Mock, memory=0, count=1, api=mock, all under the kiac.dev/ prefix

Run the check

kubectl apply -f https://raw.githubusercontent.com/saiyam1814/kiac/main/examples/gpu-mock.yaml
kubectl wait --for=jsonpath='{.status.phase}'=Succeeded \
  pod/kiac-gpu-mock-check --timeout=2m
kubectl logs pod/kiac-gpu-mock-check

mock GPU scheduling works; no hardware acceleration is enabled

The example requests kiac.dev/gpu: 1, sets runtimeClassName: kiac-gpu, and checks that allocation created the character device marker. kiac deliberately avoids the name nvidia, which distributions such as k3s may already own for a real vendor runtime. Follow the full mock GPU lab to inspect capacity, labels, verification, and cleanup.

Verify it

kiac verify cluster --name gpu-lab
kubectl get nodes -l kiac.dev/gpu.present=true
kubectl get daemonset -n kiac-gpu-system

verify checks the RuntimeClass handler, DaemonSet rollout, label contract, advertised capacity, and every GPU-labeled node. On a cluster without the flag, the global GPU checks report skip.

Path to real acceleration

The next backend uses krunkit/Venus GPU VMs as dedicated workers while keeping the workload-facing resource and labels stable. It is gated on a reproducible one-VM and two-VM performance spike, process lifecycle, SSH transport, mixed-backend inventory, and upstream libkrun work. The exact phases and current blockers are in the GPU build plan.
