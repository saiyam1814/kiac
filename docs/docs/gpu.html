Alpha · Apple silicon

Real Apple GPU nodes

Kiac can map the Mac's Apple GPU into krunkit Linux VMs and expose selected workers' Venus Vulkan devices to Kubernetes workloads through the honest kiac.dev/gpu resource.

This is Vulkan, not CUDA. The GPU is real, but the API inside the Linux guest is Mesa Venus over virtio-gpu. CUDA, NVML, nvidia-smi, Metal, and MLX are not available in pods. Kiac never advertises nvidia.com/gpu as node capacity.

Architecture

Ordinary Kiac clusters keep using the fast apple/container backend. A cluster with --gpu-workers uses krunkit and vmnet-helper for its complete topology: control plane, ordinary workers, and GPU workers. This keeps every node on one reliable VM network. Only nodes named -gpu-N publish GPU labels, receive the kiac.dev/gpu=true:NoSchedule taint, and provide schedulable GPU inventory. Kiac mounts /dev/dri only into workloads allocated through its GPU driver.

GPU mode is opt-in, so its dependencies, larger disk image, and longer first boot add no startup or idle overhead to an ordinary cluster. Existing LoadBalancer, edge proxy, storage, metrics, Gateway API, observability, verify, support, stop/start, delete, and resume paths work through the same cluster manager.

# vmnet-helper on macOS 26+

On macOS 14 or 15, use vmnet-helper's upstream installer and sudoers setup instead of Homebrew. If krunkit came from the old slp/krunkit or slp/krun tap, remove the legacy tap before reinstalling from libkrun/krun. kiac gpu doctor checks the host architecture, tool versions, SSH, disk-image, and host-network tooling, and that a Venus-capable renderer from the official krunkit dependency stack is installed.

Create a GPU cluster

K3s 1.36 with DRA is the shortest path to the complete feature:

kiac create cluster --name gpu-lab --distro k3s --k8s-version 1.36 \
  --workers 1 --gpu-workers 1 --gpu-resource-driver dra

kubectl get nodes \
  -L kiac.dev/gpu.present,kiac.dev/gpu.api,kiac.dev/gpu.memory
kiac gpu status --name gpu-lab

Kubeadm is supported too. Its pinned GPU path currently uses Kubernetes 1.37:

kiac create cluster --name gpu-ka --distro kubeadm --k8s-version 1.37 \
  --workers 1 --gpu-workers 1 --gpu-resource-driver device-plugin

The first create downloads the checksum-pinned Fedora 44 ARM64 cloud image and converts it from qcow2 to raw in process, then caches both under ~/.kiac/images. Each node gets a persistent copy-on-write disk under ~/.kiac/gpu-nodes. VM provisioning installs the pinned Kubernetes artifacts and guest packages, so the first GPU cluster is intentionally slower than an apple/container cluster.

Current topology constraints GPU clusters are IPv4-only. K3s uses its normal Flannel path. Kubeadm supports kindnet or Cilium; Cilium requires the host cilium CLI, but not --kernel full. Custom kernel paths apply only to apple/container-backed clusters.

Resource contract

ContractMeaning
kiac.dev/gpuone schedulable real Venus device per GPU worker
kiac.dev/gpu.present=truenode has passed Kiac's render-device discovery
kiac.dev/gpu.api=venusworkloads must use a Venus/Vulkan-capable userspace
kiac.dev/gpu.memoryrecorded VM-level krunkit GPU window in MiB; scheduler accounting is per node and does not prevent aggregate host unified-memory overcommit across VMs
kiac.dev/gpu=true:NoSchedulekeeps ordinary workloads off dedicated GPU workers unless tolerated
RuntimeClass/nvidiacompatibility name using the normal runtime handler; it does not install NVIDIA software

Device plugin or DRA

--gpu-resource-driver device-plugin is the default and exposes one ordinary extended resource per GPU worker. It is the simplest choice for manifests that request:

resources:
  requests:
    kiac.dev/gpu: "1"
  limits:
    kiac.dev/gpu: "1"

--gpu-resource-driver dra requires Kubernetes 1.36 or newer. The embedded node agent registers the gpu.kiac.dev driver, publishes a DeviceClass and one ResourceSlice per GPU worker, and uses CDI to inject the render device after allocation. Its extendedResourceName also lets the ordinary kiac.dev/gpu request above allocate through DRA.

For explicit capacity scheduling, a ResourceClaim can request the reported memory in 1 GiB steps; see examples/gpu-dra-memory.yaml. Capacity is scheduler accounting against krunkit's VM GPU window. It is not dedicated physical VRAM, hard per-process memory isolation, or a compute quota.

Prove the GPU path

kubectl apply -f examples/gpu-vulkan.yaml
kubectl wait --for=jsonpath='{.status.phase}'=Succeeded \
  pod/kiac-gpu-vulkan --timeout=5m
kubectl logs kiac-gpu-vulkan

The pinned test fails unless vulkaninfo identifies a real Venus device. A valid run includes output like:

deviceName = Virtio-GPU Venus (Apple M1 Max)
driverName = venus
KIAC_REAL_APPLE_GPU_OK

The workload image is digest-pinned because a generic image with a different Mesa build may expose /dev/dri without successfully enumerating Venus. The test checks the API, not just the device file.

Inference and benchmark

kiac gpu bench --name gpu-lab
kubectl apply -f examples/gpu-inference.yaml
kubectl rollout status deployment/tinyllama -n kiac-gpu-demo --timeout=10m

The benchmark uses the same revision-pinned TinyLlama Q4_K_M model and pinned ARM64 llama.cpp container for every run. It performs three Venus runs and, when host llama-bench is available, the same prompt and generation workload on native Metal. This is a regression baseline, not a promise that virtualized Vulkan equals Metal performance. Use --skip-host or -o json for automation.

Inference integrations

kiac gpu values vllm
kiac gpu values ollama
kiac gpu values kserve

These commands generate scheduling fragments, not magic CUDA conversion. Stock CUDA-oriented vLLM, Ollama, and KServe images still need to be replaced with an application image that genuinely supports Venus/Vulkan.

For a legacy manifest that hard-codes an NVIDIA resource name, enable the namespace-scoped admission rewrite explicitly:

kiac gpu compat enable --name gpu-lab --namespace demo
kiac gpu compat disable --name gpu-lab --namespace demo

The webhook rewrites supported nvidia.com/gpu requests to kiac.dev/gpu, adds the GPU toleration, and records an audit annotation. It rejects ambiguous aliases and never creates NVIDIA capacity, CUDA, or NVML.
