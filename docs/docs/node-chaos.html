Day two

Node chaos

Because every node is its own VM, stopping one is a real node failure: the kernel goes away, the kubelet goes silent, and the control plane reacts exactly like it would in production.

Stopping a node

kiac stop node worker-1 --name dev

The node argument accepts the short name (worker-1, control-plane) or the full container name (kiac-dev-worker-1). The VM halts; the container and its state remain, ready to boot again.

What to watch, in a second terminal:

kubectl get nodes -w                # the node flips Ready -> NotReady
kubectl get pods -o wide -w         # its pods get evicted and land on survivors
kubectl get events --sort-by=.lastTimestamp   # NodeNotReady, TaintManagerEviction, Scheduled

Expected timeline with stock Kubernetes defaults: the node goes NotReady within about a minute (when its kubelet lease expires), and pods with the default tolerations are evicted and rescheduled about five minutes after that (node.kubernetes.io/unreachable toleration, 300s). Deployments recover; naked pods do not, which is exactly the lesson.

If you created the cluster with --observability, open the Nodes Grafana dashboard and watch the stopped node's lines flatline while the survivors' pod counts climb.

Guard rails:

  • Stopping the control plane of a single-node cluster is refused; there would be no surviving node to observe anything.
  • Stopping the control plane of a multi-node cluster proceeds with a warning: the API server (and kubectl) is down until you start it again.

Starting it again

kiac start node worker-1 --name dev
kubectl get nodes -w    # watch it rejoin

The VM boots, the kubelet re-registers, and the node returns to Ready. Behaviors worth knowing:

LoadBalancer IPs heal themselves

vmnet may hand the VM a different IP on restart. The kubelet re-registers itself with the new address automatically, and kiac-lb notices on its next pass (~3s) that any LoadBalancer ingress IP pinned to the old address no longer belongs to an eligible node, and re-points it. There is no pool state to rebuild and nothing for you to run; see Networking.

Idempotent start

kiac start node on an already-running node just says so and exits; it is safe to run any time:

kiac start node worker-1 --name dev    # safe to run again any time

One known limitation

After a stop/start cycle, apple/container 1.0 has a vmnet issue where the restarted VM serves in-cluster traffic normally but TCP from your Mac to that specific VM is dropped. Other nodes' IPs are unaffected, and a full reboot plus kiac resume does not hit this. Details and workarounds in Troubleshooting.

Failure drills to try

  • Deploy 6 replicas across 2 workers, stop one worker, and time how long until all 6 serve traffic again.
  • Put a PVC-backed pod on a node and stop that node: local-path volumes are node-local, so watch the pod stay Pending and reason about why.
  • Stop the node that holds the EXTERNAL-IP of a LoadBalancer Service: traffic fails until the node goes NotReady, then kiac-lb re-points the IP to a surviving node on its next pass.
  • On a 3-node cluster, stop the control plane and observe that workloads keep serving while kubectl fails: the data plane outlives the control plane.

The dashboard has per-node Stop/Start buttons that shell out to these same commands. For the whole-cluster outage a Mac reboot causes, see Reboots & resume.
