Core concepts

Networking

Every node VM gets its own IP your Mac can reach. That one fact drives most of kiac's networking design, from the CNI choice to how LoadBalancers work.

vmnet and node IPs

apple/container attaches each lightweight VM to macOS's vmnet network. Each node VM therefore gets its own IP address (typically in the 192.168.64.0/24 range) that is directly routable from your Mac:

kubectl get nodes -o wide
NAME                     STATUS   ROLES           VERSION   INTERNAL-IP
kiac-dev-control-plane   Ready    control-plane   v1.36.1   192.168.64.2
kiac-dev-worker-1        Ready    <none>          v1.36.1   192.168.64.3
kiac-dev-worker-2        Ready    <none>          v1.36.1   192.168.64.4

Consequences:

  • The API server is reached at https://<control-plane-ip>:6443; the kubeconfig points there directly.
  • NodePort Services are curl-able at any node IP, no port-mapping flags or tunnels.
  • Node IPs are assigned by vmnet and can change when a VM restarts (see Node chaos for how kiac handles that).
  • Multi-node VM-to-VM networking over vmnet needs macOS 26+.

Pods use a flat pod network routed between nodes by the CNI: 10.244.0.0/16 on the kubeadm path (the CIDR kiac passes to kubeadm init), 10.42.0.0/16 on the k3s path.

vmnet's fast path and slow path

One more vmnet fact shapes performance: frames addressed to a VM's own IP are delivered fast; packets forwarded between VMs are not. Traffic that has to be routed or NATed from one node VM to another crosses vmnet's forwarded path, which is dramatically slower for bulk transfers.

kiac works with that grain everywhere:

  • Routed CNIs (kindnet) send cross-node pod traffic as pod-addressed packets, which vmnet must forward. Fine for control traffic and most dev work; slow for bulk cross-node transfers.
  • Addon placement: kiac labels one node kiac.io/lb-primary and pins the bundled Grafana and Traefik pods there, and kiac-lb prefers assigning a Service the IP of a node that hosts one of its ready endpoints. Traffic entering a node is then delivered to a local pod instead of being NATed across the slow path.
  • Cilium's overlay avoids it entirely: with --cni cilium --kernel full, cross-node pod traffic is vxlan-encapsulated in node-IP-addressed packets, which ride the fast path (~285MB/s pod-to-pod cross-node, ~1GB/s Mac-to-pod measured). See Cilium & the full kernel.

The kernel story, and why kindnet

By default each node runs Apple's minimal, optimized Linux kernel (6.12 series). It is a monolithic build tuned for fast boot: there is no module loading, and it ships without several features that mainstream CNIs assume:

  • No br_netfilter (CONFIG_BRIDGE_NETFILTER): traffic crossing a bridge cannot be steered through iptables, which silently breaks same-node Service traffic for any bridge-based CNI.
  • No VXLAN or Geneve: overlay networks like Flannel's default backend cannot form.
  • No eBPF prerequisites (BPF JIT, BTF): Cilium's datapath cannot load.

kindnet needs none of that. It ships inside the kindest/node image and uses a routed PTP (veth) topology with plain L3 routes between node IPs, which is exactly what the vmnet topology provides. That makes it the default:

kiac create cluster --cni kindnet                # default
kiac create cluster --cni cilium --kernel full   # Cilium on the full kernel; see the Cilium page
kiac create cluster --cni none                   # bring your own; nodes stay NotReady until you install one

kindnet even runs on --distro k3s: kiac disables k3s's bundled flannel outright, because flannel bridges pods onto cni0 and, on a kernel without br_netfilter, same-node pod-to-ClusterIP return traffic bypasses iptables un-DNAT and times out. kindnet's routed topology has no bridge, so the problem never exists. (--cni itself is a kubeadm-path flag; the k3s path always gets kindnet.)

Asking for --cni flannel or calico still fails fast with an explanation rather than half-installing something that cannot start. To run them anyway, boot the full kernel and bring your own manifests: --kernel full --cni none.

Honest trade-off On the stock kernel, kindnet gives you real cross-node pod networking, not a policy engine: NetworkPolicy is not enforced, and bulk cross-node throughput rides vmnet's slow forwarded path. Both limits lift with --cni cilium --kernel full.

LoadBalancer: kiac-lb on node IPs

kiac installs kiac-lb by default on kubeadm clusters. It is deliberately not a controller deployment: it is a small systemd service inside the control-plane VM that assigns node IPs to Services of type: LoadBalancer by patching their status with the node's own kubectl. No pods, no images, no RBAC, no webhooks to wait for; a Service gets its EXTERNAL-IP within a couple of seconds.

Why node IPs and nothing else: vmnet only delivers frames addressed to a VM's assigned IP. Floating virtual IPs (the classic MetalLB model, which earlier kiac releases used) can never receive traffic here, so node IPs are the only addresses that are both host-reachable and deliverable. kube-proxy programs LoadBalancer ingress IPs into iptables on every node, so a Service bound to a node IP answers on the real port, no NodePort mapping to remember.

How kiac-lb assigns an IP, on every pass of its ~3s loop:

  • Eligible nodes: Ready workers. The control-plane IP is used only on single-node clusters, keeping ports like 6443 off the LB surface.
  • Preference order: a node hosting a ready endpoint of the Service (delivery stays pod-local, avoiding the slow forwarded path), then the kiac.io/lb-primary node, then any eligible node.
  • IP sharing: Services share one node IP whenever their port sets are disjoint. The built-in addons do exactly this: Grafana (port 3000) and the Traefik gateway (80/443) ride a single worker IP on single-worker clusters.
  • Self-healing: a Service whose ingress IP stopped belonging to an eligible node (node stopped, or back from a restart with a new vmnet address) is re-pointed on the next pass; there is no pool state to rebuild. This is what makes LoadBalancers "just work" through node chaos and kiac resume.
kubectl expose deployment web --port=80 --type=LoadBalancer
kubectl get svc web    # EXTERNAL-IP is one of your worker node IPs, assigned in ~2s

# the controller's logs, from inside the control-plane VM
container exec kiac-dev-control-plane journalctl -u kiac-lb

On --distro k3s, k3s's bundled servicelb (klipper) backs type: LoadBalancer instead, natively on node IPs; kiac-lb is not installed there.

kiac also installs kiac-edge-proxy by default on every node. It is a tiny embedded node process that redirects externally-entering TCP for NodePorts and LoadBalancer service ports into a built-in original-destination TCP proxy, then opens a fresh local connection back to the original Service address. That keeps kube-proxy in charge of backend selection while avoiding apple/container vmnet's TSO stall on large uploads from sibling VMs. Disable it only with --no-edge-proxy.

Skip the LoadBalancer controller with --no-lb if you prefer NodePorts only. Note that --gateway requires the LoadBalancer.
