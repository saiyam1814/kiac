Troubleshooting

Start with kiac doctor; it catches most environment problems. The rest of this page is the known failure modes and what they mean.

First move: kiac doctor

kiac doctor        # checks macOS, apple/container, the system service, kubectl, arm64
kiac doctor --fix  # also starts the container system service if it is stopped

What --fix actually runs is container system start. You can run that yourself, and inspect the service with container system status. kiac also starts the service automatically during create preflight.

"cluster already exists"

Error: cluster "dev" already exists; delete it first with: kiac delete cluster --name dev

Node VMs from a previous create (even stopped ones) still carry the cluster's name. If you want the old cluster back, resume it; if not, delete and recreate:

kiac resume cluster --name dev     # bring the existing cluster back
# or
kiac delete cluster --name dev
kiac create cluster --name dev --workers 2

After a reboot: clusters show 0/N

kiac get clusters
NAME  STATUS
dev   0/3 stopped

A reboot (or container system stop) halts every node VM; their disks persist. 0/N stopped is the signal to resume:

kiac resume cluster --name dev

resume boots the VMs and heals everything the fresh vmnet IPs broke: apiserver cert, kubeconfigs, worker kubelets, and kube-proxy. It is idempotent, so re-running after a partial failure is the retry. The full story is on Reboots & resume. Two caveats: it heals kubeadm clusters only (recreate k3s clusters; they build in under a minute), and expect the control-plane VM to die and be rebooted once during resume after an IP change; that is part of the normal flow.

Create fails partway

kiac tears down the half-created node VMs automatically (you will see cleaned up partial cluster "dev"), so just fix the cause and re-run. Common causes:

  • macOS older than 26: multi-node networking needs macOS 26+. Try a single-node cluster, or upgrade.
  • Timeout on a loaded machine: raise it with --wait 10m.
  • Cluster name too long: a node's container name is also its Linux hostname, capped at 63 characters. kiac rejects names that would overflow; use a shorter name.

LoadBalancer EXTERNAL-IP stays <pending>

  • Created with --no-lb? Nothing is installed to assign IPs.
  • On kubeadm clusters, kiac-lb assigns IPs within seconds. If a Service stays pending, read the controller's logs from inside the control-plane VM: container exec kiac-dev-control-plane journalctl -u kiac-lb. A "no conflict-free node IP" line means every eligible node IP already has that Service's ports claimed.
  • On k3s clusters, k3s's bundled servicelb assigns the IPs after pulling its klipper-lb pod image inside the VM, so the first Service can take a minute or two; its pods are the svclb-* pods in kube-system.
  • For Grafana specifically: kubectl get svc -n kiac-observability grafana; for the gateway: kubectl get svc -n kiac-gateway traefik.
  • A node that was stopped or restarted is handled automatically: kiac-lb re-points any ingress IP that stopped being an eligible node IP on its next pass (~3s). See Networking.

kubectl top shows <unknown>

metrics-server needs about 60 seconds after cluster creation for its first scrape. If it never resolves, check the metrics-server pod in kube-system.

Cilium preflight errors

Both Cilium prerequisites are checked before any VM boots, so these cost seconds, not minutes:

Error: --cni cilium needs the full node kernel: add --kernel full (or a --kernel path)
Error: --cni cilium drives the official installer, which is not on PATH; install it with: brew install cilium-cli

The fixes are literal: add --kernel full, and brew install cilium-cli. See Cilium & the full kernel.

"flannel/calico needs kernel features"

Error: flannel needs kernel features the stock node kernel does not enable; use
--cni cilium with --kernel full, or --cni none to bring your own

Not a bug: Apple's minimal node kernel ships without br_netfilter, VXLAN, and the eBPF machinery, and kiac does not bundle flannel or Calico manifests. Cilium is the supported path to a policy-enforcing CNI (--cni cilium --kernel full); on the full kernel you can also install flannel or Calico yourself with --kernel full --cni none. The kernel story is in Networking.

Kernel downloads and the ~/.kiac cache

--kernel full downloads the published kernel release asset (about 15MB) into ~/.kiac/kernels/ on first use, and the k3s path caches the CNI plugins archive under ~/.kiac/. Every artifact is sha256-verified against a checksum pinned in the kiac binary, on download and again on every cache hit, so:

  • A sha256 mismatch error means the download was corrupted (or the cache tampered with); the file is discarded, just re-run.
  • Deleting ~/.kiac is always safe; kiac re-downloads and re-verifies on the next create.
  • Offline? The first --kernel full or --distro k3s create needs the network once; after that the cache serves.

Restarted node VM unreachable from the Mac

Known limitation in apple/container 1.0's vmnet handling: after kiac stop node + kiac start node, the restarted VM serves in-cluster traffic normally, but host-to-that-VM TCP connections are dropped. Symptoms: pods on the node are fine and other nodes reach it, but curling a NodePort or LoadBalancer IP on that specific node from your Mac hangs.

  • Traffic through the other nodes' IPs is unaffected; kiac-lb prefers pod-local IPs, so re-creating the pod on another node (or just deleting the pod and letting it reschedule) usually restores host access.
  • A full reboot plus kiac resume cluster does not hit this; it is specific to restarting a single VM while the container system service keeps running.

kubectl: "no route to host" on a freshly created cluster

Unable to connect to the server: dial tcp 192.168.64.5:6443: connect: no route to host

Same apple/container vmnet family as above, seen right after kiac create: the API server is healthy inside the control-plane VM (container exec kiac-<name>-control-plane kubectl get nodes works, Grafana on a LoadBalancer IP works), but your Mac cannot reach the control-plane VM's IP on 6443. "no route to host" is an ARP/L3 failure for that one VM IP, not a port or TLS problem: vmnet did not make that VM host-reachable, often a stale ARP entry left over from a deleted cluster whose control plane reused the same lease. kiac now checks this at the end of create and, when it fails, prints the recovery instead of a kubectl hint that would only error.

The cluster is fine; use it from inside the VM, or reset vmnet and resume to restore host access:

# use it right now, from inside the control-plane VM
container exec kiac-dev-control-plane kubectl get nodes

# restore kubectl from your Mac: reset vmnet, then heal the cluster
container system stop && container system start
kiac resume cluster --name dev

A full container system restart tears down and rebuilds vmnet (clearing the stale ARP state), and kiac resume re-points every node, kubeconfig, and certificate SAN at the fresh IPs. This is being tracked upstream at apple/container; see issue #6.

Cross-node bulk transfers are slow

Expected on routed CNIs (kindnet): cross-node pod traffic takes vmnet's slow forwarded path. Control traffic and ordinary dev workloads are fine; bulk data transfers are where it shows. --cni cilium --kernel full avoids it entirely via the vxlan overlay (~285MB/s cross-node measured). See Networking.

Large uploads to a NodePort from another VM stall (TSO)

Older kiac clusters, or clusters created with --no-edge-proxy, can hit an apple/container vmnet offload interaction: a large HTTP body (roughly 200 KiB or more) sent from another Apple Container VM to a kiac NodePort stalls after the first ~150-300 KiB and then times out, while small requests and health checks pass. The sending VM's TCP segmentation offload (TSO) hands the virtual NIC oversized segments that get mangled on the way through the kiac node's NodePort DNAT into the pod. Confirmed on both kindnet and Cilium, so it is not CNI-specific.

Current kiac installs kiac-edge-proxy by default. It redirects externally-entering TCP for NodePorts and LoadBalancer service ports into a tiny node-local original-destination proxy, terminating the sender's TCP connection on the node and opening a fresh local connection that kube-proxy can DNAT safely. Check it with:

container exec kiac-dev-control-plane ps -ef | grep '[k]iac-edge-proxy'
container exec kiac-dev-control-plane tail -50 /var/log/kiac-edge-proxy.log

If you deliberately disabled the edge proxy, the remaining sender-side workaround is to disable TSO before the request (needs NET_ADMIN):

container run --rm --cap-add NET_ADMIN --network default alpine:3.20 sh -lc '
  apk add --no-cache curl ethtool >/dev/null
  ethtool -K eth0 tso off        # the one setting that matters
  curl --request PUT --data-binary @big-file http://NODE_IP:NODEPORT/'

This is the apple/container vmnet limitation tracked in issue #8; the default edge proxy is kiac's built-in mitigation.

"--gateway needs the built-in LoadBalancer"

--gateway exposes Traefik through a type: LoadBalancer Service, so it cannot be combined with --no-lb. Drop --no-lb.

kubectl suddenly times out

Did you stop the control-plane node? On multi-node clusters kiac stop node control-plane proceeds with a warning, and the API server is down until:

kiac start node control-plane --name dev

Kubeconfig looks wrong

kiac only touches entries named kiac-<cluster>, and the first time it modifies your kubeconfig it saves the original to ~/.kube/config.kiac.bak. kiac delete cluster removes exactly the cluster's entries and clears current-context if it pointed there.
