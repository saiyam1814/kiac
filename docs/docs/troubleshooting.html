Troubleshooting

Start with kiac doctor; it catches most environment problems. The rest of this page is the known failure modes and what they mean.

First move: kiac doctor

kiac doctor        # checks macOS, apple/container, the system service, kubectl, arm64
kiac doctor --fix  # also starts the container system service if it is stopped

What --fix actually runs is container system start. You can run that yourself, and inspect the service with container system status. kiac also starts the service automatically during create preflight.

"cluster already exists"

Error: cluster "dev" already exists; delete it first with: kiac delete cluster --name dev

Node VMs from a previous create (even stopped ones) still carry the cluster's name. Delete and recreate:

kiac delete cluster --name dev
kiac create cluster --name dev --workers 2

This is also the fix after a reboot, see below.

After a reboot: clusters show 0/N

kiac get clusters
NAME  STATUS
dev   0/3 stopped

A Mac reboot does not preserve running lightweight VMs: the container service forgets them, so every node of every cluster is gone. 0/N stopped is that signal. Clusters do not survive reboots today; delete and recreate:

kiac delete cluster --name dev
kiac create cluster --name dev --workers 2

Persistent clusters (backed by container machine) are on the roadmap. Until then, treat clusters as cheap and disposable, and keep the definition in a config file so recreating is one command.

Create fails partway

kiac tears down the half-created node VMs automatically (you will see cleaned up partial cluster "dev"), so just fix the cause and re-run. Common causes:

  • macOS older than 26: multi-node networking needs macOS 26+. Try a single-node cluster, or upgrade.
  • Timeout on a loaded machine: raise it with --wait 10m.
  • Cluster name too long: a node's container name is also its Linux hostname, capped at 63 characters. kiac rejects names that would overflow; use a shorter name.

LoadBalancer EXTERNAL-IP stays <pending>

  • Created with --no-lb? MetalLB is not installed; there is nothing to assign IPs.
  • Check the pools exist: kubectl get ipaddresspools -n metallb-system. If the pool step failed at create time, kiac says so in the create output (the cluster still works otherwise).
  • For Grafana specifically: kubectl get svc -n kiac-observability grafana; for the gateway: kubectl get svc -n kiac-gateway traefik.
  • After stopping and starting a node, its IP may have changed; kiac start node <node> --name <cluster> re-syncs the MetalLB pool and is safe to re-run. See Node chaos.

kubectl top shows <unknown>

metrics-server needs about 60 seconds after cluster creation for its first scrape. If it never resolves, check the metrics-server pod in kube-system.

"flannel/calico/cilium needs kernel features"

Error: cilium needs kernel features (br_netfilter, VXLAN, eBPF) that Apple's stock
node kernel does not enable; use kindnet, or --cni none with a custom kernel
(tracked on the roadmap)

Not a bug: Apple's minimal node kernel ships without those features. kindnet is the supported CNI today; the full story is in Networking.

"--gateway needs the built-in LoadBalancer"

--gateway exposes Traefik through a type: LoadBalancer Service, so it cannot be combined with --no-lb. Drop --no-lb.

kubectl suddenly times out

Did you stop the control-plane node? On multi-node clusters kiac stop node control-plane proceeds with a warning, and the API server is down until:

kiac start node control-plane --name dev

Kubeconfig looks wrong

kiac only touches entries named kiac-<cluster>, and the first time it modifies your kubeconfig it saves the original to ~/.kube/config.kiac.bak. kiac delete cluster removes exactly the cluster's entries and clears current-context if it pointed there.

Still stuck?

Open an issue with the failing command's output: github.com/saiyam1814/kiac/issues.
