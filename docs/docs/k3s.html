Distros & kernels

k3s distro

The same one-VM-per-node clusters, built on rancher/k3s instead of kubeadm: a single binary as PID 1 in every VM, an sqlite datastore, and a 2-node cluster ready in well under a minute.

kiac create cluster --distro k3s --name dev --workers 1

How it differs from the kubeadm path

The default distro boots kindest/node images (systemd, containerd, kubeadm) and initializes the cluster with kubeadm init/join. With --distro k3s, each VM boots a pinned rancher/k3s image and runs the k3s binary directly as PID 1: no systemd in the VM, no separate etcd, no kubeadm. The server keeps its state in sqlite, workers join as k3s agents over the standard K3S_URL/K3S_TOKEN mechanism, and the kubeconfig merges into ~/.kube/config as kiac-<name>, exactly like the kubeadm path.

Kubernetes versions work the same way: minors 1.32 through 1.36 map to digest-pinned rancher/k3s images (1.36 default), selected with the same --k8s-version flag:

kiac create cluster --distro k3s --k8s-version 1.34

What k3s bundles, and what kiac does with it

k3s ships its own batteries, so on this path kiac keeps the pieces that behave well inside Apple Container VMs and swaps out the pieces that do not:

PieceOn the k3s pathOpt out
Storagek3s's bundled local-path provisioner (default StorageClass)--no-storage
Metricsk3s's bundled metrics-server; kubectl top nodes works natively--no-metrics
LoadBalancerkiac-lb, the same tiny controller used by the kubeadm path; k3s's bundled servicelb is disabled because it advertises every node IP, including nodes that would forward large uploads across vmnet--no-lb
Ingressk3s's bundled Traefik is disabled: it would fight the --gateway addon's Traefik for ports 80 and 443always off
Network policyk3s's network-policy controller is disabled; it only works against the flannel bridge kiac removes (see below)always off

The optional addons work with the same flags as everywhere else: --observability installs Prometheus and Grafana, --gateway installs the Gateway API CRDs plus Traefik with the ready-to-use kiac Gateway. kiac-lb assigns their LoadBalancer IPs, kiac labels a primary node (kiac.io/lb-primary) the addon pods pin to, and the default edge proxy handles large external uploads through NodePorts and LoadBalancers.

Why kindnet replaces flannel

k3s normally brings flannel as its CNI. kiac starts the server with --flannel-backend=none and applies kindnet instead, for a kernel reason:

  • Apple's stock node kernel has no VXLAN, so flannel's default backend cannot form an overlay in the first place.
  • Even flannel's host-gw backend wires pods onto a cni0 bridge, and the kernel also lacks br_netfilter. On a bridge without it, same-node pod-to-ClusterIP return traffic bypasses iptables un-DNAT and every same-node service call times out.
  • kindnet uses a routed PTP (veth pair) topology instead of a bridge, so all pod traffic stays visible to iptables. It is the same CNI the kubeadm path uses, configured for k3s's default 10.42.0.0/16 pod CIDR.

kindnet's config references the upstream ptp CNI plugin, which k3s's own multicall binary does not implement. kiac downloads the official containernetworking plugins release (v1.7.1, sha256-verified, cached once under ~/.kiac/) and streams the needed binaries into every node VM.

Because the CNI is fixed on this path, --cni is a kubeadm-only flag; passing it with --distro k3s is an error.

Footprint

Measured on Apple silicon with the default sizing (4 vCPUs per node, 4G control plane, 2G workers):

  • A 2-node k3s cluster (server + 1 agent) is Ready in roughly 22 to 54 seconds, image pull excluded.
  • Host memory for the whole 2-node cluster sits around 3.7GB RSS idle.

That makes --distro k3s the fastest way to a disposable cluster, while the kubeadm path stays the closer match for clusters you operate with kubeadm in production.

Honest trade-offs

  • kiac resume is supported. A tiny launcher stored on each agent replaces only its stale K3S_URL after vmnet changes the server address; no extra daemon, proxy image, or token copy is added. Resume also waits for current Node IPs, refreshes host-network pods, heals the edge proxy, and rewrites the host kubeconfig. Existing k3s clusters are upgraded in place on their first resume.
  • No --cni cilium. The Cilium path (and --kernel pairing) is a kubeadm-path feature; see Cilium & the full kernel.
  • sqlite, single server. There is one k3s server; workers are agents. Control-plane HA is out of scope for a laptop cluster.
  • k3s's bundled ServiceLB is intentionally disabled. kiac-lb publishes one endpoint-local node IP instead of every node IP, so LoadBalancer clients do not accidentally choose a cross-node large-upload path.
