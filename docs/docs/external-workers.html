External K3s workers

Use a Linux VM on your Mac as a worker in an existing K3s cluster. kiac join worker provisions one owned Fedora/krunkit VM and connects it through an operator-managed WireGuard peer.

Alpha scope This path supports IPv4 K3s with its existing Flannel VXLAN network and an exact matching pinned K3s release. Kubeadm, other CNIs, dual-stack and remote GPU registration are outside this alpha. The external cluster's routing and WireGuard peer must already be prepared.

How it connects

The worker advertises its stable WireGuard address as its Kubernetes InternalIP. Kiac retains a separate private vmnet DHCP address for local VM management. The tunnel runs inside the guest; Kiac does not alter your Mac's routes, firewall or VPN.

ConnectionPurpose
Mac → private vmnet addressKiac provisions and manages its owned worker VM.
Guest kiacwg0 → existing WireGuard peerThe worker reaches the external API and cluster routes through the tunnel.
Existing cluster nodes ↔ worker VPN addressBidirectional node and Flannel traffic uses the routes prepared by the operator.

This is a CPU worker. Krunkit exposes Venus to its guests, but the external-worker path installs no GPU resource driver and advertises no Kiac GPU resource. For local GPU scheduling, see Apple GPU (beta).

Requirements

  • Apple silicon Mac and optional VM backend. Install krunkit 1.3.2+, vmnet-helper 0.13.0+, its helper service and the renderer dependencies described in the backend setup. Apple/container is not required for this path. Kiac uses its verified Fedora 44 image and pinned K3s ARM64 binary.
  • Available host disk space. Joining requires at least 7 GiB on the krunkit state filesystem before downloads or boot: 4 GiB reserve plus 3 GiB for the new VM. This is a thin-provisioning estimate; it does not reserve space or guarantee that later guest-disk growth will fit.
  • Matching external cluster. The server must use one of Kiac's pinned K3s releases, IPv4 and Flannel VXLAN. The exact server and worker releases must match. Supply the cluster's actual pod and service CIDRs.
  • Prepared WireGuard peer. Use a reachable numeric IPv4 endpoint and a peer already authorized for this worker. The API's TLS certificate must cover the VPN API address. Every remote node must have bidirectional VPN routes to the worker, and Flannel must use reachable node addresses and interfaces.
  • Trusted secure token. Obtain the full CA-pinned K3s secure token through your trusted cluster administration channel. Prefer the agent token from the server's /var/lib/rancher/k3s/server/agent-token. Short tokens are refused. Treat the token and WireGuard private key as secrets.

A suitable peer is a reachable Linux gateway or control plane forwarding the existing cluster's node, pod and service routes. The guest initiates UDP through vmnet NAT and sends periodic keepalives. The peer must route return traffic to the worker's /32 while preserving the node addresses used by Flannel. The outer WireGuard endpoint must remain outside the tunnel routes.

Flannel nodes exchange UDP 8472 through the tunnel. K3s normally carries control-plane-to-kubelet requests through the agent's outbound WebSocket tunnel; direct inbound kubelet TCP 10250 requirements depend on the cluster's egress-selector mode. Opening the API port alone does not establish pod-network reachability.

Prepare private files

Store the secure token as agent-token and the single-peer WireGuard configuration as worker.conf, with owner-only permissions:

chmod 600 agent-token worker.conf

For example, worker.conf contains:

[Interface]
Address = 10.250.76.2/32
PrivateKey = <worker-private-key>

[Peer]
PublicKey = <gateway-public-key>
Endpoint = 192.0.2.10:51820
AllowedIPs = 10.250.76.0/24, 10.42.0.0/16, 10.43.0.0/16
PersistentKeepalive = 25

Replace the example endpoint and keys with your peer's details. AllowedIPs must cover the VPN API and the complete declared pod and service CIDRs. Those CIDRs must be distinct from the API address, worker VPN range and VM management range. Tunnel routes must not overlap the guest's vmnet management /24.

Kiac refuses symlinks, special files, hooks, DNS endpoints, default routes, multiple peers and unsupported WireGuard fields. Supported fields are Address, PrivateKey, optional MTU (1280–1420), and one peer's PublicKey, optional PresharedKey, Endpoint, AllowedIPs and optional PersistentKeepalive (1–120 seconds). Defaults are MTU 1420 and keepalive 25 seconds; the guest interface is kiacwg0.

Join the worker

kiac join worker --name remote-lab \
  --server https://10.250.76.1:6443 \
  --token-file ./agent-token --wireguard-config ./worker.conf \
  --node-ip 10.250.76.2 --k8s-version 1.37 \
  --pod-cidr 10.42.0.0/16 --service-cidr 10.43.0.0/16

Adapt every address and CIDR to your cluster. --k8s-version accepts a pinned minor or exact release. Kiac defaults to two vCPUs, 2G memory, a 20G persistent disk and a ten-minute readiness wait.

FlagAccepted range
--cpus1–32
--memory1–60G
--disk8–1024G
--waitPositive duration, up to one hour; package installation has a separate bounded ten-minute minimum budget

The K3s agent verifies the token's CA hash before sending credentials. Kiac uses the agent's own kubelet certificate to observe its Node, verifies the owner label, VPN InternalIP, exact API and kubelet release, Flannel VXLAN pod CIDR, initial taint and Ready condition, then pins the Node UID. A successful join proves registration and readiness; verify application traffic for your topology separately.

Opt workloads in

New workers carry kiac.dev/external-worker=true:NoSchedule so ordinary workloads do not land on a laptop just because it joined. DaemonSets and other workloads that already tolerate all taints can still schedule. Add a matching selector and toleration to the intended workload:

spec:
  nodeSelector:
    kiac.dev/external-worker: "true"
  tolerations:
    - key: kiac.dev/external-worker
      operator: Equal
      value: "true"
      effect: NoSchedule

This fragment belongs under the Pod spec; for a Deployment, put it under spec.template.spec. An operator may deliberately remove the taint after a successful join. Later start worker respects that choice.

Lifecycle and retry

kiac get workers
kiac get workers -o json
kiac logs worker remote-lab
kiac stop worker remote-lab
kiac start worker remote-lab --wait 10m

Starting verifies the original Node UID and VPN address again and waits for the Node's reported boot ID to match the current guest boot ID. A cached Ready condition from an earlier boot does not satisfy this check. The fixed WireGuard and K3s units start on guest boot.

Failures before agent startup remove only the newly created owned local VM. Once startup may have registered a remote Node, Kiac retains the VM and its node-password with phase joining. Fix the network or cluster issue and run kiac start worker remote-lab to retry with the same identity and the saved guest files, even if the original host credential files are gone. Ownership mismatches or cleanup failures also retain inventory.

Credentials cross the management channel through standard input and remain in private files inside the guest. Host inventory under ~/.kiac/workers contains public identity and a CA hash, not the token or WireGuard private key. Worker logs redact the saved token, its credentials and private WireGuard keys inside the guest before returning output to the host. Command failures omit private remote output.

Separate inventory and lifecycle External workers use a kiacx-worker-… VM namespace. Cluster delete, resume, verify, support bundles and the web UI do not manage them. Stopping affects only the local VM and does not drain remote workloads.

Drain remotely, then delete locally

Use your external-cluster credentials to drain workloads and remove the remote Node first. Obtain its VM/Node name from kiac get workers -o json and substitute your own context and node:

kubectl --context YOUR_EXTERNAL_CONTEXT drain NODE_NAME --ignore-daemonsets
kubectl --context YOUR_EXTERNAL_CONTEXT delete node NODE_NAME
kiac delete worker remote-lab

kiac delete worker removes only its owned local VM and inventory. It never calls the external cluster's administrative API. If you remove the VM first, draining or deleting the remote Node remains your responsibility. Kiac does not configure the external control plane, other nodes, CNI, addons or your host kubeconfig.

Completed alpha validation

The v0.11.0 acceptance run used two VMs on separate vmnet subnets on the same Mac, connected through a controlled WireGuard lab. It verified bidirectional pod-IP traffic, DNS and ClusterIP access, scheduling opt-in through the worker taint, the same Node UID after stop/start, log-secret redaction and local deletion preserving the remote Node.

This is completed lab validation, not a claim of cloud or production readiness. Different gateways, routing policies and external clusters need their own connectivity and workload validation. Host sleep/wake is not part of this acceptance record.

The source guide is also available as docs/external-worker-alpha.md.
