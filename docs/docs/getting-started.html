Getting started

From an empty Mac to a deployed, reachable app in four steps.

1. Check your setup

kiac doctor

Doctor verifies five things: macOS 26+ (multi-node networking needs it; single-node may still work on older versions), the apple/container CLI at 1.0.0 or newer (excluding incompatible 1.2.0; use 1.2.1+), the container system service, kubectl on your PATH, and an arm64 CPU.

If the container system service is stopped:

kiac doctor --fix    # runs: container system start

2. Create a cluster

kiac create cluster --name dev --workers 2

What happens, step by step:

  1. Preflight checks, then the pinned kindest/node:v1.37.0 image is pulled.
  2. Three node VMs boot in parallel (1 control plane + 2 workers), each with 4 vCPUs; the control plane gets 4G of memory and workers 2G by default (--cpus, --cp-memory, --memory).
  3. kubeadm initializes the control plane and joins the workers concurrently.
  4. kindnet (the CNI) is applied, then the default addons install: local-path storage and metrics-server in parallel, followed by the kiac-lb LoadBalancer (a tiny systemd service inside the control-plane VM).
  5. Nodes are waited on until Ready, a primary LoadBalancer node is labeled, the kiac-edge-proxy node process is installed for large external uploads, and the kubeconfig is written.

Useful variations:

kiac create cluster                          # single node named "dev", control plane untainted
kiac create cluster --k8s-version 1.34       # pick a Kubernetes minor (kubeadm 1.32-1.37 pinned)
kiac create cluster --distro k3s --workers 1 # k3s nodes, ready in under a minute; see k3s distro
kiac create cluster --cni cilium --kernel full # Cilium on the full kernel; see the Cilium page
kiac create cluster --observability --gateway # everything on; see the addon pages
kiac create cluster --config cluster.yaml    # declarative; see Config file

A failed create cleans up its half-built node VMs automatically, so your machine never ends up with orphans.

3. The kubeconfig

On create, kiac merges the cluster's credentials into your kubeconfig (~/.kube/config, or $KUBECONFIG when it points at a single file) and switches the current context:

  • The context, cluster, and user are all named kiac-<name>, e.g. kiac-dev.
  • The server address is the control-plane VM's IP on port 6443, reachable directly from your Mac.
  • The first time kiac touches your kubeconfig it saves a backup at ~/.kube/config.kiac.bak, and never overwrites that backup afterwards.
  • kiac delete cluster removes exactly those entries again.
kubectl config current-context    # kiac-dev
kubectl get nodes -o wide         # note: every node has its own INTERNAL-IP

Need a standalone kubeconfig file (for a tool or another shell)? The dashboard offers a per-cluster download.

4. First deploy

Because kiac-lb is installed by default and assigns node IPs, a plain type: LoadBalancer Service gets a real address within seconds:

kubectl create deployment web --image=nginx
kubectl expose deployment web --port=80 --type=LoadBalancer
kubectl get svc web
NAME   TYPE           EXTERNAL-IP    PORT(S)        AGE
web    LoadBalancer   192.168.64.3   80:30495/TCP   15s

Then curl it straight from your Mac, no tunnels, no port-forwarding:

curl http://$(kubectl get svc web -o jsonpath='{.status.loadBalancer.ingress[0].ip}')

Local images without a registry

Build with apple/container and load the image into every node's containerd:

container build -t myapp:dev .
kiac load image myapp:dev --name dev

Set imagePullPolicy: IfNotPresent (or Never) in your pod spec so the kubelet uses the loaded image.

Rebooted your Mac?

A reboot halts every node VM, but the cluster is not lost. Bring it back, healed, with one command:

kiac resume cluster --name dev

See Reboots & resume for what gets healed and why.

Clean up

kiac get clusters            # NAME  STATUS (e.g. dev  3/3 running)
kiac delete cluster --name dev
