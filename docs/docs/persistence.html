Reboots & resume

Clusters survive host reboots. One command boots the node VMs back up and heals everything a fresh set of IPs breaks.

kiac resume cluster --name dev

What a reboot actually does to a cluster

Rebooting your Mac (or stopping its VM services) halts every node VM. The VMs' disks persist, so nothing is lost, but two things change on the next boot:

  • Kiac's merged runtime inventory reports every node as stopped; kiac get clusters shows 0/N stopped.
  • vmnet hands out fresh IPs. Node addresses are not stored anywhere; every boot gets the next free one.

What becomes stale depends on the distro. kubeadm pins the control-plane address into its serving certificate, kubeconfigs, static pod manifests, worker kubelet configs, and kube-proxy ConfigMap. k3s persists the original server address in each agent VM's startup environment, while host-network pod objects can retain their previous Node IP. Resume detects the distro and repairs the corresponding state.

kiac resume cluster

kiac get clusters
NAME  STATUS
dev   0/3 stopped

kiac resume cluster --name dev
 ✓ Preflight checks
 ✓ Booting 3 node VM(s)
control-plane IP changed 192.168.64.2 -> 192.168.64.5; healing certs and kubeconfigs
 ✓ Healing control-plane files
 ✓ Pointing worker kubelets at the control plane
 ✓ Waiting for the API server
 ✓ Re-pointing kube-proxy and cluster-info
 ✓ Waiting for nodes to be Ready
 ✓ Writing kubeconfig

On a kubeadm cluster, the steps heal:

  • Control-plane files: the old IP is rewritten to the new one across admin.conf, super-admin.conf, the scheduler, controller-manager, and kubelet configs, and the four static pod manifests. The apiserver serving certificate is regenerated for the new address when needed, and the kubelet restarts to pick everything up.
  • Workers: each worker's kubelet.conf is pointed at the new control-plane address and its kubelet restarted.
  • In-cluster state: the kube-proxy ConfigMap (its pods crash-loop against the old address until then) is rewritten and the daemonset restarted, along with kube-public/cluster-info.
  • Your kubeconfig: the kiac-<name> context is re-merged with the new server address.
  • LoadBalancer IPs: nothing to do explicitly. kiac-lb reads the healed admin.conf on every pass, so any Service ingress IP pinned to a dead address is re-pointed within seconds. See Networking.

One expected kubeadm oddity: the control-plane VM may die once during its first boot after an IP change (an artifact of the node image's own IP fixup). resume detects that, boots it again, and says so; it is part of the normal flow, not a failure.

On a K3s cluster, resume starts the server first, writes its current URL to a root-only file on each agent, and restarts only agents whose live K3S_URL is stale. Resume then waits until every Kubernetes Node reports its VM's current address, refreshes host-network pods, heals the node-local edge proxies, and writes the host kubeconfig. Ordinary clusters use the tiny PID-1 launcher and recreate kindnet; GPU clusters reconcile the persistent K3s systemd services, which refreshes bundled Flannel, and recreate optional node-exporter pods. Existing ordinary K3s clusters are migrated automatically on first resume without touching their join token.

Measured end to end: kubeadm resumed a 3-node cluster across a vmnet subnet change in 46 seconds. k3s resume has also been exercised repeatedly across fresh addresses, including an existing-cluster migration and cross-node 1 MiB uploads after recovery.

Idempotent by design

Every healing step is a no-op once applied, so kiac resume cluster is safe to run at any time:

  • On a running cluster, it degenerates to a status check plus no-op heals.
  • After a partial failure (say, the Mac went to sleep mid-resume), re-running it is the retry; the worker heal even matches any previous address, so a resume that died halfway stays repairable.
  • When the IPs happen to come back unchanged, it is just start + wait.
kiac resume cluster --name dev --wait 10m   # loaded machine? give it longer

What survives a reboot

  • All Kubernetes objects (etcd's data directory is on the control-plane VM's persistent disk).
  • PVC data: local-path volumes are directories on node disks, which persist.
  • Images loaded with kiac load image: they live in each node's containerd store.
  • The kiac-lb systemd unit: it is enabled in the VM, so it comes back with the node.

Limits, honestly

  • --cni none clusters never report nodes Ready, so the final readiness wait warns instead of failing; the VMs and apiserver are still up.
  • IPv6-only kubeadm clusters still require recreation after a reboot. IPv4 and dual-stack clusters are supported; k3s supports IPv4 and dual-stack creation and resume.
  • resume is not start node. A single node stopped with kiac stop node just needs kiac start node; resume is for the whole-cluster outage a reboot causes (though running it in that state is harmless).
