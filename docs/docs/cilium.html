Distros & kernels

Cilium & the full kernel

Apple's stock node kernel cannot run Cilium. kiac ships a published, sha-pinned kernel build that can, and one flag pair boots your nodes on it and drives the official Cilium installer.

kiac create cluster --name dev --workers 2 --cni cilium --kernel full

Prerequisites

RequirementDetail
cilium CLI on your Macbrew install cilium-cli. kiac drives the official installer; if the binary is missing, create fails with exactly that hint before any VM boots.
--kernel full (or a --kernel path)Cilium's eBPF datapath needs kernel features the stock node kernel lacks; --cni cilium without a kernel is refused up front rather than producing agents in a crash loop.
kubeadm distroThis is the default; --cni (and with it the Cilium path) does not apply to --distro k3s.

What --kernel full is

Node VMs normally boot the runtime's default kernel: a minimal, monolithic build with no module loading and no VXLAN, br_netfilter, or eBPF JIT. --kernel full swaps in a kernel kiac builds in CI (.github/workflows/kernel-build.yml) from two pinned inputs: Apple's containerization base config and kiac's kernel/config-full fragment. On top of the base it enables:

  • VXLAN and Geneve: overlay datapaths (Cilium's tunnel mode, flannel's vxlan backend).
  • br_netfilter and nf_tables: bridged traffic steered through iptables/nftables, which bridge-based CNIs assume.
  • BPF JIT and BTF: the eBPF machinery Cilium's datapath loads.
  • WireGuard and kprobes: transparent encryption and the tracing hooks tools like Hubble and Tetragon build on.

The kernel stays monolithic with zero loadable modules, matching Apple's model, and its version (6.12.28) matches the kernel apple/container 1.0.0 boots by default, minimizing guest ABI drift.

Supply-chain mechanics: the first --kernel full downloads the release asset (about 15MB) from the kernel-v6.12.28-full GitHub release into ~/.kiac/kernels/. Its sha256 is pinned inside the kiac binary and verified on download and on every cache hit, so a corrupted or tampered cache can never boot a node. You can also pass your own build: --kernel /path/to/Image takes any uncompressed arm64 boot Image.

kiac create cluster --kernel full                 # full kernel, default kindnet CNI
kiac create cluster --kernel full --cni cilium    # full kernel + Cilium
kiac create cluster --kernel full --cni none      # full kernel, bring your own CNI

The performance story

vmnet, the macOS network kiac nodes live on, has a fast path and a slow path. Frames addressed to a VM's own IP are delivered fast; packets that have to be forwarded between VMs (as routed CNIs like kindnet do for bulk cross-node pod traffic) take a much slower path.

Cilium's vxlan tunnel datapath sidesteps this: cross-node pod traffic is encapsulated in packets addressed to the destination node's IP, which rides the fast path. Measured on this stack:

  • Cross-node pod-to-pod bulk transfer: ~285MB/s.
  • Mac-to-pod: ~1GB/s.

On the stock kernel with a routed CNI, the same bulk transfers crawl through vmnet's forwarded path. The full Networking page tells the fast/slow path story in detail.

Cilium also brings real NetworkPolicy enforcement to kiac clusters, which kindnet does not do; the eBPF datapath is the actual production datapath, not a simulation.

Full walkthrough

1. Install the prerequisite and create the cluster. The addon flags compose: this exact command (Cilium + observability + Gateway API) builds the whole stack in about 1m37s on an M-series machine, kernel download included on the first run.

brew install cilium-cli
kiac create cluster --name dev --workers 2 --cni cilium --kernel full --observability --gateway

The kernel is fetched and verified before anything boots (cached after the first run), the VMs boot on it, and the Installing CNI (Cilium) step runs cilium install --wait against the new cluster. Kiac passes its --wait value to Cilium as --wait-duration; raise it on slow links so large image pulls can finish.

2. Check Cilium. The same CLI kiac used is yours to drive:

cilium status --wait
kubectl get nodes -o wide           # all Ready on the Cilium datapath
kubectl -n kube-system get pods -l k8s-app=cilium

3. Deploy something and route to it. With --gateway on, the Gateway API CRDs, Traefik, and a default Gateway (kiac in kiac-gateway) are already accepted, so an HTTPRoute is all you write:

kubectl create deployment web --image=nginx
kubectl expose deployment web --port=80

cat <<'EOF' | kubectl apply -f -
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: web
spec:
  parentRefs:
    - name: kiac
      namespace: kiac-gateway
  hostnames: ["web.local"]
  rules:
    - backendRefs:
        - name: web
          port: 80
EOF

4. Curl it from your Mac.

GW=$(kubectl get svc traefik -n kiac-gateway -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
curl -H "Host: web.local" http://$GW/
<!DOCTYPE html> ... Welcome to nginx! ...

5. Try a NetworkPolicy. Something kindnet clusters cannot do:

cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-web
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes: [Ingress]
EOF
curl -m 3 -H "Host: web.local" http://$GW/   # times out: Cilium enforces the policy
kubectl delete networkpolicy deny-web

With --observability on, Grafana is on its own LoadBalancer IP (port 3000) next to the gateway; the create output prints both URLs.

Operational details

  • Both prerequisites are checked before any VM boots, so a missing cilium binary or kernel costs seconds, not minutes.
  • The kernel cache lives at ~/.kiac/kernels/; deleting it just triggers a fresh verified download next time.
  • --cni flannel works on the same kernel: kiac embeds the upstream v0.28.9 manifest (VXLAN backend, no host CLI needed) and streams the bridge delegate plugin from its sha-verified archive into every node. --cni calico is not wired up yet and fails fast.
  • --kernel and --distro are CLI flags only for now; they are not config file keys yet.
